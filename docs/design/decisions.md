# 결정과 근거

작성: 2026-10-30
관련: [ticket-pivot.md](ticket-pivot.md), [ticket-plan.md](ticket-plan.md), 리서치 원문 [../research/](../research/)

willnew 의 큰 결정마다 무엇을 정했고, 무엇을 근거로 했고, 그 근거가 얼마나 단단한지 적는다. 근거 등급은 셋이다.

- **확인**: 원문(논문 PDF, 공식 보고서 페이지)을 열어 수치와 문장을 확인했다
- **2차**: 초록, 보도, 요약 글로만 봤다. 말할 때 "보고에 따르면" 을 붙인다
- **가설**: 내 판단이다. 직접 재서 확인할 계획이 있다

## 1. 프로젝트가 걸어 온 길

| 10-29 (전환) | CS 와 AI 가 대화해 티켓을 만들고, 개발자가 자기 터미널에서 푼다. AI 는 통역 | 아래 2절 |

## 2. 결정별 근거

### D1. AI 를 "고치는 자리" 에서 "통역하는 자리" 로 옮긴다

| 근거 | 등급 | 내용 |
|---|---|---|
| Bettenburg 외, "What Makes a Good Bug Report?", FSE 2008 | 확인 | Apache, Eclipse, Mozilla 개발자와 제보자 466명 설문. 개발자가 도움이 된다고 본 재현 단계(83%), 스택 트레이스(57%), 테스트 케이스(51%)는 제보자가 제공하기 가장 어려운 정보와 같았다. 가장 심각한 문제는 재현 단계 오류와 불완전한 정보 |
| Stack Overflow Developer Survey 2025 | 확인 | AI 정확도 불신 45.7%, 신뢰 32.7%(응답 33,244건). 불만 1위 "거의 맞지만 완전히는 아닌 답" 66%. "AI 코드 디버깅이 더 오래 걸린다" 45.2% |
| Faros AI 2025 (개발자 1만 명 이상, 1,255팀) | 확인, 벤더 자료 | AI 도입이 높은 팀은 PR 리뷰 시간 91% 증가, PR 크기 154% 증가. 회사 수준 성과와 유의한 상관 없음. 상관 자료라는 점을 같이 말한다 |
| Atlassian State of DevEx 2025 (3,500명) | 확인 | 50% 가 주 10시간 이상을 조직 비효율로 잃는다. 코딩에 쓰는 시간은 16%. 팀 간 협업이 순위 상승. CS 와 개발 사이 번역을 따로 재지는 않았다 |
| "틀려도 싸고 사람이 바로 고칠 수 있는 자리에 AI 를 둔다" | 가설 | CS 가 초안을 확인하고 원문이 같이 붙으면 정리가 틀려도 손해가 작다. 코드 변경은 틀리면 리뷰와 신뢰 비용이 크다 |


### D2. "AI 에게 맡기기" 는 버리지 않고 작은 일의 선택지로 남긴다

| 근거 | 등급 | 내용 |
|---|---|---|
| Peng 외, Copilot 대조실험, arXiv 2302.06590 (2023) | 확인(초록) | HTTP 서버 구현 과제에서 Copilot 사용군이 55.8% 빨랐다. 참가자 수는 초록에 없음 |
| 에이전트 PR 병합률 연구 | 2차 | 전체 병합률 약 71%, 문서 84%, 버그 수정 64%. 에이전트가 올린 PR 만 본 것이라 선택 편향이 있다 |
| METR 2025 (16명, 246건) | 확인, 조건 붙임 | AI 를 쓰면 19% 더 오래 걸렸다. 단 METR 가 2026-02 후속(57명, 800건 이상)에서 결과를 스스로 신뢰하기 어렵다고 밝혔다. "AI 가 느리게 만든다" 로 단정하지 않는다 |


### D3. 양식(템플릿)만으로 부족한지는 직접 비교해서 정한다

| 근거 | 등급 | 내용 |
|---|---|---|
| Sülün 외, GitHub 이슈 템플릿 연구, TOSEM 2024 | 2차(초록) | 100개 대형 프로젝트, 이슈 190만 건 이상. 템플릿이 있는 프로젝트가 해결이 빠르고 댓글이 적었다. 상관 연구이고, 개발자가 직접 쓰는 오픈소스 이슈라 CS 가 고객 말을 전하는 상황과 다르다 |
| BURT (ESEC/FSE 2022, ICSE 2023 시연) | 확인(시연 논문) | 대화형 되묻기가 템플릿 양식보다 재현 단계 오류(8.3% 대 20.4%)와 누락은 적었지만 관찰 동작은 더 부정확했다(54건 중 16건 대 8건). 18명 평가. LLM 기반 아님 |
| 실무 논의(Reddit, HN) | 2차 | 긴 필수 양식은 회피되거나 의미 없는 글자로 채워진다. 결과를 못 보는 블랙홀 효과가 제보 동기를 꺾는다 |

결정: 평가에 "AI 없음(필수 칸 양식만)" 비교군을 넣는다. AI 가 양식보다 못한 일에서는 AI 를 뺀다. 양식만 쓰는 모드도 제품에 남긴다.


### D4. 중복 문의는 버리지 않고 합친다

| 근거 | 등급 | 내용 |
|---|---|---|
| Bettenburg 외, "Duplicate Bug Reports Considered Harmful ... Really?", ICSM 2008 | 확인 | 개발자 대부분이 중복을 심각한 문제로 보지 않았고, 중복이 추가 정보(버전, OS, 첨부, 스택 트레이스 등)를 준다고 답했다. 저자들은 병합을 제안 |

### D5. 되묻기를 차별점으로 내세우지 않고, 근거 있는 되묻기와 역방향 통역을 내세운다

| 근거 | 등급 | 내용 |
|---|---|---|
| Atlassian Rovo Bug Report Assistant | 확인(공식 문서) | 티켓이 생긴 뒤 댓글로 부족한 정보를 묻는다. Jira 플랜에 포함 |
| Linear agent + Zendesk, Intercom 연동 (2025-12) | 확인(공식 changelog) | 지원 대화를 읽어 이슈를 만든다. Business 플랜 이상 |
| iTop AI Assistant | 2차 | 자체 호스팅 ITSM 에서 질문 최대 3개 |
| 조사한 제품 중 용어 사전 기반 코드 매핑, 개발자 답의 역방향 통역, 칸별 출처를 하는 곳 | 찾지 못함 | 검색 범위 안의 결과이고 부재 증명은 아니다 |

결정: 티켓 도구로 경쟁하지 않는다. Jira, Linear 위에 얹는 통역 계층으로 말한다. 데모 첫 장면은 용어 사전 근거 질문과 `willnew ask` 역방향 통역.


### D6. AI 는 로컬(Ollama) 기본이고 일을 칸 하나 단위로 쪼갠다

| 근거 | 등급 | 내용 |
|---|---|---|
| 지원 티켓 개인정보와 외부 LLM 전송 문제 | 2차(실무 아키텍처 글) | 결정론적 도구로 먼저 가리고 로컬 모델로 처리하는 구조가 권장된다. LLM 에게 가리기를 맡기면 누락 위험 |
| Laban 외, "LLMs Get Lost In Multi-Turn Conversation", 2025 | 2차(초록) | 다중 턴에서 성능이 단일 턴보다 평균 39% 낮았다. 초기 가정에 묶여 회복하지 못한다 |
| Active Task Disambiguation, ICLR 2025 | 2차(초록) | 모델이 제로샷으로 만든 질문은 정보량으로 고른 질문보다 효율이 낮다 |
| ClarifyGPT, FSE 2024 | 2차(초록) | 모호할 때만 묻는 구조로 GPT-4 Pass@1 70.96% → 80.80% |
| Acharya, Ginde, EASE 2025 | 2차(초록) | 미세조정한 Qwen 2.5 가 비정형 제보를 템플릿으로 바꾸는 일에서 ChatGPT-4o 3-shot 과 비슷했다(CTQRS 77% 대 75%) |

결정: 대화 상태는 모델 기억이 아니라 구조화된 칸으로 들고 간다. 물을 칸은 규칙이 고르고 모델은 질문 문장만 만든다. 형식은 JSON 스키마로 강제한다.


### D7. 생성으로 채우지 않고 되물어서 채운다, 칸마다 출처를 단다

| 근거 | 등급 | 내용 |
|---|---|---|
| ChatBR, ASE 2024 | 2차(초록) | 빠진 항목을 ChatGPT 가 생성해 채운다. 생성 정보의 의미 유사도 평균 84.10% |
| Tam 외, ACL Findings 2023 | 2차(초록) | LLM 이 원문 문장을 그대로 담은 틀린 요약에 오히려 점수를 더 주는 경향 |
| Ji 외, 환각 서베이, ACM Computing Surveys 2023 | 2차 | 생성 과제 전반의 환각 정리 |

결정: 제보자가 말하지 않은 사실을 만들지 않는다. 빈 칸은 묻고, 칸마다 출처(고객의 몇 번째 말, 어느 문서, 어느 티켓)를 단다. 출처 없는 칸은 "추정" 이고 CS 가 하나씩 확인해야 보낼 수 있다. 출처가 붙어 있다고 맞다고 보지도 않는다.

### D10. 효과는 아직 가설이고, 재는 방법을 먼저 정했다

| 근거 | 등급 | 내용 |
|---|---|---|
| CS 에서 개발로 넘어갈 때의 비용, 재현 불가율, 재오픈율 공개 수치 | 찾지 못함 | 벤더 블로그 수치(에스컬레이션 15~30%, 8배 비용)는 출처가 불분명해 쓰지 않는다. 한국 정량 자료도 찾지 못했다 |
| Salesforce 엔지니어링 사례 | 확인, 방법 미공개 | 에스컬레이션 중 33% 는 지원 단계에서 해결 가능했고, 25% 는 고객이 먼저 찾은 버그, 42% 는 복잡한 연동 |
| 100건 골든 세트의 신뢰구간 | 직접 계산 | 80% 가 나와도 Wilson 95% 구간은 약 71~87% |

결정: M-1 인터뷰와 시범 운영에서 도입 전후를 직접 잰다(되묻는 횟수, 재오픈, 접수에서 작업 시작까지). 평가는 출처 셋으로 나누고 신뢰구간, 판정 일치율(kappa), 쌍 비교를 같이 적는다. 친구와의 검증은 사용성만 본다고 밝힌다.


### D11. 팀 서버가 에이전트를 돌리지 않는다 (B3 를 접은 이유)

| 근거 | 등급 | 내용 |
|---|---|---|
| Claude Code 법무 문서 | 확인 | "route requests through Free, Pro, or Max plan credentials on behalf of their users" 금지. 사용자가 자기 구독으로 수정하지 않은 바이너리에 로그인하는 것은 막지 않는다 |
| Anthropic AUP | 2차 | "services that route requests through consumer subscriptions" 금지 |

결정: 코드 작업은 개발자가 자기 PC, 자기 계정으로 한다. 서버 AI 는 정리와 통역만 하고 로컬 모델이나 회사 API 키로 돈다. 허브와 러너, held 같은 장치는 브랜치로 보관한다.


## 3. 남은 한계

1. **실사용 데이터가 없다**: 효과는 가설이다. 재는 방법과 비교군을 먼저 정했고, AI 가 양식보다 못하면 빼도록 설계했다
2. **로컬 모델 품질을 아직 모른다**: 등급별 실측과 비교표는 M3 에서 나온다. 그 전에는 숫자를 말하지 않는다
3. **혼자 만들어서 운영 경험이 없다**: 서버 가용성, 백업, 동시성은 운영해 보지 않았다. 그래서 머리 없는 서버, SQLite WAL, 대기열처럼 검증된 단순한 방법만 골랐다
4. **경쟁 제품이 빠르다**: Linear agent, Rovo, 채널톡 ALF 가 같은 자리로 올 수 있다. 그래서 티켓 도구가 아니라 그 위의 통역 계층으로 자리를 잡고, 팀이 소유하는 용어 사전과 로컬 우선을 앞세운다
5. **아직 원문을 직접 확인하지 않은 근거**: Runeson ICSE 2007 본문, ChatBR 본문, BURT FSE 2022 본문, Sülün 외 TOSEM 2024 본문(해결 시간 수치)
