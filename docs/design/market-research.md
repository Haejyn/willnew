## A. 요약 결론

1. **"제보자가 주는 정보" 와 "개발자가 필요한 정보" 의 불일치는 학술적으로 가장 널리 인용되는 사실이다.** Bettenburg·Zimmermann 외(ACM FSE 2008, Apache·Eclipse·Mozilla 조사)는 개발자가 가장 필요로 하는 것(재현 단계, 스택 트레이스, 테스트 케이스)이 제보자가 가장 제공하기 어려운 것과 정확히 겹친다고 밝혔다.
2. **중복 리포트는 흔하고, 버리기보다 합치는 편이 낫다.** Bettenburg 외(ICSM 2008)는 Anvik 외를 인용해 Mozilla 리포트의 약 30%, Eclipse 의 약 20% 가 중복이라고 쓴다. 같은 논문의 설문에서 개발자 대부분은 중복을 심각한 문제로 보지 않았고 중복이 추가 정보를 준다고 답했으며, 저자들은 중복을 버리지 말고 병합하자고 제안한다. 이는 willnew 의 F1(새 티켓 대신 영향 고객과 단서를 기존 티켓에 추가)과 맞는다. 재오픈 비율은 신뢰할 수 있는 원문 수치를 찾지 못했다(Zimmermann 외 ICSE 2012 는 Microsoft 엔지니어 358명 설문으로 재오픈 원인을 분석했지만 비율은 익명 처리했다).
3. **"템플릿만 두면 된다"(C21)는 실무에서 반복해서 실패한다.** Reddit·Hacker News 논의에서 긴 필수 양식은 (a) 제보자 인지 부담으로 `"안 돼요"` 같은 한 줄 제보로 회피되거나, (b) 필수 칸을 통과하려고 의미 없는 글자를 채워 넣는(template fatigue) 결과를 낳는다.
4. **대신 학계와 업계가 수렴한 해법은 두 갈래다.**
   - **자동 맥락 수집**: Jam.dev, Marker.io 처럼 말로 쓰게 하지 않고 화면·콘솔·네트워크·환경을 자동으로 찍어 붙인다.
   - **대화형 되묻기**: Song 외의 **BURT**(ESEC/FSE 2022, ICSE 2023 도구 시연)는 Android 사용자에게 관찰 동작(OB), 기대 동작(EB), 재현 단계(S2R)를 대화로 묻는다. 18명 평가에서 템플릿 양식보다 재현 단계의 오류(8.3% 대 20.4%)와 누락은 적었지만 관찰 동작은 더 부정확했다(54건 중 16건 대 8건). LLM 기반은 아니다. Bo 외(ASE 2024)의 **ChatBR** 은 되묻지 않고, BERT 로 빠진 항목을 찾은 뒤 ChatGPT 로 채운다.
5. **국내 실무에서는 "채널톡 → Slack → Jira" 자동화가 사실상의 표준 워크플로다.** Velog, 티스토리, 디스콰이엇 등에서 Zapier/Make, 슬랙 이모지 트리거, Jira Automation 으로 VOC 를 옮기는 구축기가 다수 공유된다. 즉 "도구 사이를 잇는 수요" 는 이미 검증돼 있다. 다만 대부분 **운반만 자동화**할 뿐, 모호한 원문이 그대로 Jira 티켓이 되는 문제는 남아 있다.
6. **경쟁 제품은 이미 강하다 (가장 조심할 지점).**
   - **Atlassian Rovo (Jira Triage Agent / Bug Report Assistant)** 와 **Linear Triage Intelligence** 가 분류, 중복 탐지, 담당자 추천, 심지어 부족한 버그 리포트 보완까지 제품 안에 넣었다.
   - **Plain**(Vercel, Cursor 등이 사용), **Pylon**, **Linear Asks** 는 CS 채널(Slack, 이메일, 인터콤)과 Linear 이슈를 양방향으로 묶어 상태가 바뀌면 CS 에게 자동으로 알린다.
7. **따라서 willnew 가 "일반적인 AI 티켓 요약/분류" 로 승부하면 진다.** 경쟁 제품이 아직 비워 둔 자리는 네 가지가 합쳐진 지점이다: **(1) 티켓 생성 전 팀 지식(해결된 티켓·용어 사전)에 기반한 출처 있는 되묻기, (2) 고객 원문을 외부 클라우드로 보내지 않는 로컬(Ollama) + 결정론적 개인정보 마스킹 구조, (3) 개발자 터미널(`willnew work`)과 수용 기준 테스트 초안으로 이어지는 마지막 구간, (4) 개발자 답변을 CS 언어로 바꾸는 역방향 통역.**

## C. 경쟁·유사 제품 비교 (C1 대응)

"Linear 나 Jira 에 이미 있지 않나" 라는 지적에 답하는 표다.

| 제품 | 하는 일 | 잘 푸는 부분 | willnew 와 비교해 비어 있는 자리 |
|---|---|---|---|
| **Atlassian Rovo** (Jira Triage Agent, Bug Report Assistant) | Jira/JSM 안에서 티켓 자동 분류, 우선순위·담당자 제안, 중복 탐지, Confluence 문서 연결, 버그 리포트 작성 보조 | 대기업 Jira 생태계, 문서 연동 | 클라우드 전용, 무거운 JSM 전제, 개발자 터미널(`work`) 연결 없음, 소규모 팀엔 과함 |
| **Linear Asks + Triage Intelligence** | Slack/이메일에서 `/asks` 로 이슈 생성, 과거 이슈 기반 자동 담당자·라벨·중복 제안 | 빠른 UI, Slack 입구, 중복 제안 | 티켓이 **들어온 뒤** 분류함. 제출 전에 CS 와 대화하며 빠진 재현 단계를 캐묻는 과정이 약함. 클라우드 전용 |
| **Plain** (Vercel, Cursor 등 사용) | 개발자 중심 B2B 지원 툴. 대화 스레드에서 바로 Linear 이슈 생성·연결, Linear 완료 시 지원 스레드 상태 자동 갱신, MCP 지원 | 지원 스레드 ↔ 이슈 양방향 상태 동기화 | 지원 도구 자체를 통째로 바꿔야 함. 개발자 답변을 비개발자 언어로 풀어 쓰는 통역보다는 기술 팀 대상 |
| **Pylon** | B2B Slack/Intercom 지원과 Linear 연결, 고객 계정(ARR 등) 기반 라우팅, 완료 시 `Waiting on You` 로 자동 전환 | 고객 영향도 집계, 상태 자동 회신 | B2B 고객 채널 관리 도구. 티켓 생성 전 대화형 명세화와 로컬 AI 는 아님 |
| **Jam.dev / Marker.io** | 브라우저 확장·위젯으로 화면 녹화, 콘솔 로그, 네트워크 요청, OS·브라우저를 원클릭 수집해 Linear/Jira 로 전송 | **말로 재현 단계를 쓰게 하지 않고 증거를 바로 찍음** | CS 가 고객 말을 전해 듣고 대신 올리는 상황(고객 화면을 직접 못 찍는 상황)에서는 여전히 대화 정리가 필요함 |
| **Intercom Fin** | 고객과 직접 채팅하며 문서 기반으로 1차 답변, 안 되면 사람에게 넘김 | 사용법 질문 자동 방어(F1 의 `question`) | 고객 응대 챗봇이지 엔지니어링 티켓 명세 도구가 아님 |
| **학술 프로토타입: BURT, ChatBR** | BURT 는 대화로 OB, EB, S2R 을 묻고, ChatBR 은 빠진 항목을 LLM 으로 채운다 | 되묻기와 보강 기법 검증 | 연구용 프로토타입. 팀 용어 사전, 실제 저장소와 터미널 연결, 역방향 통역 없음 |

### 이 비교에서 나온 willnew 의 정확한 자리

> **"Jam.dev 가 화면 증거를 찍고, Linear/Jira 가 이슈를 보관한다면, willnew 는 그 사이에서 '사람 말로만 전해진 모호한 문의' 를 팀 지식과 대화를 통해 근거 있는 티켓과 터미널 작업으로 바꾸는 로컬 우선 통역 계층이다."**

## D. 반대 증거와 기획 수정

리서치에서 나온 반대 증거는 무시하지 않고 기획을 고치는 데 쓴다.

1. **"사람에게 재현 단계를 글로 쓰게 하는 것 자체가 틀렸다. 화면 녹화나 자동 로그가 낫다"** (Reddit·HN, Jam.dev 의 철학)
   - **반영**: 대화를 길게 끌지 않는다. 고객 ID 나 에러 시각이 있으면 F11(맥락 어댑터)로 로그를 먼저 붙이고, 이미 로그로 확인된 것은 CS 에게 묻지 않는다. 또한 HAR 파일이나 Jam.dev/Loom 링크를 붙이면 질문 수를 줄인다.
2. **"제보자가 양식을 안 채우는 건 답이 안 돌아오는 블랙홀 때문이지 양식이 몰라서가 아니다"** (HN)
   - **반영**: F7(진행 상황과 완료를 CS 의 쉬운 말로 돌려주는 루프)과 Pylon 식의 `고객에게 답할 차례` 표시가 단순 부가 기능이 아니라 **CS 가 다음번에도 도구를 쓰게 만드는 핵심 유인**이다.
3. **"중복 티켓을 막아 버리면 추가 재현 단서를 잃는다"** (Bettenburg 외 ICSM 2008)
   - **반영**: F1 에서 중복으로 판단했을 때 제보를 버리지 않는다. 기존 티켓에 `영향 고객 +1` 만 하는 게 아니라 **이번 제보의 원문과 새 환경·재현 단서를 타임라인에 덧붙인다.**
4. **"이미 Slack + Jira 를 쓰는데 도구를 또 깔기 싫다"** (국내 블로그 사례들)
   - **반영**: C5, C23 보완대로 Slack 입구와 Jira 내보내기를 미루지 않는다.

## E. 리서치로 보강한 M-1 인터뷰 질문지

과거 행동만 묻는다("있으면 쓰시겠어요?" 같은 미래 가정 질문은 금지).

1. (CS·개발 공통) **최근 2주 안에 고객 문의가 개발팀으로 넘어간 실제 사례 하나**를 떠올려 주세요. 처음 고객이 뭐라고 했고, 해결될 때까지 메시지가 몇 번 오갔나요?
2. (개발자) 받은 제보에서 **가장 자주 빠져 있어서 다시 물어보게 되는 정보 1~2가지**는 무엇인가요? (Bettenburg 논문의 재현 단계·환경·기대 결과 중 무엇인지 확인)
3. (개발자) 제보를 받고 **`재현 안 됨` 으로 닫거나 보류한 최근 사례**가 있나요? 그때 무엇이 있었으면 재현할 수 있었을까요?
4. (CS) 개발팀에 넘길 때 **양식(템플릿)이 있나요?** 있다면 채우기 가장 막막한 칸은 어디고, 모를 때는 어떻게 하시나요?
5. (CS) 개발자에게 답변을 받았을 때 **고객에게 그대로 전달하기 어려워서 다시 물어본 적**이 있나요?
6. (CS) 같은 문제로 여러 고객이 문의할 때 **이미 개발팀에 넘어간 문제인지 어떻게 확인**하시나요?
7. (리드·보안) 고객 문의 원문을 **외부 AI(ChatGPT, Claude 등)에 붙여 넣는 것에 대한 사내 규정이나 걱정**이 있나요?

## F. 한계 (솔직하게 밝힐 것)

- 국내 중견·스타트업의 **정량 설문**(예: "국내 개발자 N% 가 CS 티켓 품질에 불만")은 공개된 중립 자료를 찾지 못했다. 정량 수치는 해외 학술 연구(Bettenburg 2008, Runeson 2007, Zimmermann 2012)를 인용하되, 오픈소스·대기업 데이터라는 맥락을 함께 밝혀야 한다.
- 따라서 국내 소규모 팀 맥락은 **M-1 의 직접 인터뷰 5명 이상**으로 메우는 것이 여전히 필요하다.
