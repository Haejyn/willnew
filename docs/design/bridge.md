# willnew 다음 방향: 비개발자와 개발자 사이의 AI 브리지

상태: B1, B2 구현 완료 (PR #4, #5). B3 구현 중 (2026-10-23)

## 한 줄 정의

CS, 디자이너, PM 같은 비개발자가 업무 채팅에 올린 말을 AI가 개발자가 바로 판단할 수 있는 작업 명세와 구현 제안으로 바꾸고, 개발자가 승인하면 브랜치에서 에이전트가 작업한 뒤 테스트, 검토, 병합, 배포까지 이어 주는 오픈소스 도구.

지금 willnew 는 "맡기면 고쳐서 올린다" 에 무게가 있다. 다음 방향은 그 앞쪽, 사람과 사람 사이의 번역과 합의에 무게를 옮긴다. 코드를 고치는 에이전트는 이미 많다. 비개발자 요청이 개발자에게 닿기 전에 정리되고, 개발자 판단이 비개발자에게 이해되는 형태로 돌아가는 부분은 비어 있다.

## 풀려는 문제

| 지금 일어나는 일 | 원인 | willnew 가 하는 일 |
|---|---|---|
| 디자이너가 "좀 더 여유 있게" 라고 하면 개발자는 몇 px 인지 되묻는다 | 요청에 측정 가능한 기준이 없다 | 요청을 받자마자 AI가 빠진 정보를 요청자 말투로 되묻고, 답을 수용 기준(px, 색 토큰, 문구)으로 정리한다 |
| 개발자가 "그건 안 돼요" 라고만 해서 감정이 상한다 | 이유와 대안이 전달되지 않는다 | 개발자의 짧은 판단을 요청자용 설명(왜, 대안 2개, 각각 걸리는 시간)으로 풀어 준다 |
| 다 만든 뒤 "이게 아닌데요" 가 나온다 | 만들기 전에 합의한 기록이 없다 | 작업 전에 "이렇게 개발할까요?" 제안을 양쪽이 확인하고, 그 합의를 명세로 남긴다 |
| 디자이너는 코드 리뷰를 못 하고, 개발자는 화면 확인을 미룬다 | 확인 수단이 역할마다 다르다 | 디자이너에게는 미리보기 링크와 전후 스크린샷, 개발자에게는 diff 와 테스트 결과를 따로 보여 준다 |
| 누가 무엇을 왜 정했는지 나중에 다툰다 | 결정이 채팅에 흩어진다 | 요청마다 결정 기록(누가, 언제, 무엇을, 근거)을 남긴다 |

## 흐름

```
요청자 채팅 ─▶ 1 정리 ─▶ 2 되묻기 ─▶ 3 작업 명세 ─▶ 4 구현 제안 ─▶ 5 개발자 확인
                                                                    │
     10 요청자에게 답 ◀─ 9 배포 ◀─ 8 병합 ◀─ 7 양쪽 확인 ◀─ 6 브랜치 작업과 검증
```

1. 정리: 채팅 원문, 첨부 스크린샷, Figma 링크를 읽고 요청 유형(버그, 화면 수정, 문구, 데이터)을 정한다
2. 되묻기: 수용 기준을 세우는 데 빠진 것만 요청자에게 묻는다. 최대 3개, 선택지로. 예: "버튼 간격은 어느 쪽이에요? 8px / 12px / 16px"
3. 작업 명세: 문제, 기대 결과, 수용 기준, 범위 밖, 참고 자료를 한 장으로 만든다. 요청자 화면에는 쉬운 말 요약, 개발자 화면에는 기술 명세
4. 구현 제안: 에이전트가 저장소를 읽고 "이렇게 개발할까요?" 를 만든다. 바꿀 파일, 접근 방법, 위험, 예상 시간과 비용, 추가할 테스트
5. 개발자 확인: 승인, 고쳐서 승인, 직접 할게, 거절(사유) 중 하나. 거절하면 사유를 요청자용 설명으로 풀어 대안과 함께 돌려준다
6. 브랜치 작업과 검증: 요청마다 브랜치. 수용 기준은 테스트로 먼저 쓰고, 검증 명령으로 판정. 실패하면 로그를 붙여 1회 재작업
7. 양쪽 확인: 요청자는 미리보기 링크와 전후 스크린샷으로 "의도대로예요" 를 누르고, 개발자는 diff 와 테스트로 승인한다. 둘 다 끝나야 병합
8. 병합: 지금의 `--ship merge|pr` 그대로
9. 배포: `--deploy-check` 그대로
10. 요청자에게 답: 지금처럼 승인한 개발자 이름으로 쉬운 말 답장

AI 가 하는 일은 판단 대신이 아니라 번역과 정리다. 범위, 우선순위, 승인은 항상 사람이 정한다.

## 역할별 화면

| | 요청자 (CS, 디자이너, PM) | 개발자 |
|---|---|---|
| 채팅에서 보는 것 | 내 말을 정리한 요약, AI 의 되묻기, 진행 단계, 쉬운 말 답 | 기술 명세, 구현 제안 카드, 위험 표시 |
| 확인하는 것 | 미리보기 링크, 전후 스크린샷, 문구 | diff, 테스트, 충돌, 비용 |
| 누르는 버튼 | 의도대로예요 / 다시 봐 주세요 | 진행 / 고쳐서 진행 / 직접 할게 / 거절 |
| 첫 화면 | 내 요청 | 내 차례 (확인할 제안, 승인할 결과) |

같은 스레드를 역할마다 다르게 렌더링한다. 메시지 하나에 `forRequester` 와 `forDeveloper` 두 본문을 두고, 원문은 접어서 항상 볼 수 있게 한다. 번역이 원문을 가리지 않는 것이 신뢰의 조건이다.

## 디자이너와 개발자 사이에서 추가로 할 것

- Figma 링크를 받으면 Figma MCP 로 해당 프레임의 크기, 간격, 색, 글꼴을 읽어 수용 기준에 숫자로 넣는다
- 색과 간격을 디자인 토큰 이름으로 바꿔 쓴다. 토큰에 없는 값이면 "새 값을 넣을지, 가장 가까운 `space-3` 을 쓸지" 를 양쪽에 묻는다
- UI 를 바꾼 결과에는 전후 스크린샷을 같은 크기로 나란히 붙인다 (Playwright)
- 요청자가 "다시 봐 주세요" 를 누르면 스크린샷 위에 표시를 그려 남길 수 있다. 그 표시는 다음 시도의 수용 기준이 된다

## 지금 구조에서 바꿀 것

| 지금 | 바꾼 뒤 |
|---|---|
| 채팅 메시지 → triage → 바로 run | 채팅 메시지 → Request(정리, 되묻기, 명세, 제안) → 개발자 확인 → run |
| Run 이 요청의 전부 | Request 가 요청의 전부이고 Run 은 그 안의 실행 기록 (1 요청에 여러 run) |
| 승인은 결과에 한 번 | 확인 지점 셋: 구현 제안(개발자), 결과 화면(요청자), 결과 코드(개발자) |
| 봇 메시지 한 가지 본문 | 메시지마다 요청자용과 개발자용 본문 |
| 계획 에이전트가 템플릿만 고름 | 계획 에이전트가 되묻기, 명세, 제안까지 만든다 (읽기 전용 권한) |

Request 상태:

```
draft → clarifying → spec_ready → proposed → approved → building → verifying
      → preview (요청자 확인) → code_review (개발자 확인) → merged → deployed → closed
      (어느 단계든 → declined | cancelled)
```

## 실행 주체와 약관

팀이 쓰면 누구의 AI 로 돌리느냐가 문제다. 한 사람의 구독으로 팀원 요청을 자동으로 처리하는 것은 이용 조건에 맞지 않는다. 그래서 개인 구독은 개발자가 직접 맡은 일에만 쓰고, 자동 처리와 맡기 전 단계는 회사 API 키나 클라우드 계정으로 돌린다 (근거는 `hub-runner.md` 약관 검토). 두 가지를 지원한다.

1. 러너 모드(기본): 구현 제안을 승인한 개발자의 PC 러너가 그 개발자의 로그인으로 돌린다 (`hub-runner.md`). "확인한 사람이 실행한다" 가 이번 흐름과 맞는다
2. 조직 API 키 모드(선택): 회사 Anthropic API 키로 서버가 Claude Agent SDK 를 돌린다

정리, 되묻기, 명세, 번역은 작은 모델(Haiku)로 돌려 비용을 낮춘다. 코드 작업만 큰 모델을 쓴다.

## AX 지표

도입한 팀이 "AI 로 일하는 방식이 바뀌었다" 를 숫자로 보여 줄 수 있어야 한다.

- 요청부터 배포까지 걸린 시간 (중앙값)
- 개발자에게 닿기 전에 해결된 되묻기 수 (사람 사이 왕복을 줄인 횟수)
- 첫 제안 승인율, 결과 첫 확인 통과율
- 개발자 1인이 요청 1건에 쓴 시간 (확인 버튼까지 걸린 시간 합)
- 요청 1건 비용 (AI 토큰)

지표는 모두 기록에서 계산한다. 가정치(절약 시간)는 가정이라고 표시한다.

## 오픈소스로 찾히고 쓰이게 하기

### 검색과 AI 답변에 잡히기 (SEO, GEO, AEO)

AI 검색(ChatGPT, Perplexity, Claude, Google AI 개요)은 정의가 분명하고, 비교가 있고, 사실이 출처와 함께 적힌 페이지를 인용한다.

- 영어 README 를 기본으로, 한국어는 `README.ko.md`. 첫 문장을 그대로 인용될 수 있는 정의 문장으로 쓴다
- 카테고리 단어를 일관되게 쓴다: "AI bridge between non-developers and developers", "design-to-dev handoff", "Claude Code agent orchestration", "Slack bot for engineering requests", "AX (AI transformation)"
- 문서 사이트(GitHub Pages)에 `SoftwareApplication`, `FAQPage` JSON-LD, `llms.txt` 와 `llms-full.txt`, sitemap, OG 이미지
- 비교 문서: willnew 와 Devin, GitHub Copilot coding agent, Linear 에이전트, Sweep 의 차이를 사실만으로. 어디서 겹치고 어디서 다른지
- 질문으로 검색되는 내용(설치, 비용, 보안, 약관)은 FAQ 로 따로 둔다
- 수치는 실측 조건과 함께 적는다. AI 답변이 인용할 때 근거가 따라간다
- GitHub: description, topics(`claude-code`, `ai-agents`, `slack-bot`, `developer-tools`, `design-handoff`, `code-review`, `agentic-workflow`, `llm`, `ax`), social preview 이미지, homepage 링크

### 스타를 받는 데 실제로 효과가 큰 것

- 설치 없이 써 보기: 데모 모드는 서버 없이 돈다. GitHub Pages 에 `/?demo` 를 올려 README 첫 화면에서 바로 누르게 한다
- 30초 GIF: 디자이너 요청 → 되묻기 → 제안 → 확인 → 배포 → 답장
- 한 줄 설치: `npx willnew`
- 기여 입구: CONTRIBUTING, good first issue, 이슈 템플릿, Discussions, CHANGELOG, 릴리스 노트
- 출시: Show HN, GeekNews, Product Hunt, r/ClaudeAI, awesome-claude-code 류 목록, X

스타 수는 보장할 수 없다. 위 항목은 방문자가 써 보기까지의 마찰을 줄이는 일이다.
